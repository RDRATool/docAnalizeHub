## 2. データモデル（グラフ定義）

### 2.1 ノード種別

| 種別 | key | 生成元 | 概算件数 |
| --- | --- | --- | --- |
| `doc` | `{deck}#{slide}` | .md ファイル 1 件 = 1 ノード | 182 |
| `func` | `func:{正規化ID}` | 2.2.3 / 2.3.3 新機能一覧の行 | ~214 |
| `flow` | `flow:{系統}:{番号}` | 2.2.1 / 2.3.1 一覧 + 2.2.2 / 2.3.2 詳細 | ~60 |
| `entity` | `ent:{エンティティ名}` | 2.2.4 / 2.3.4 / 別.3.5 取扱データ一覧 | ~120 |
| `system` | `sys:{システム名}` | データフロー図 / システム関連図 / 他システムI/F一覧 | ~20 |
| `actor` | `actor:{ロール名}` | 業務フロー本文の `(担当者)` + 権限一覧のヘッダ | ~25 |
| `external` | `ext:{ファイル名}` | `「...xls」` 等の外部資料参照 | ~5 |
| `request` | `req:{番号}` | 改善要望No. | ~15 |

### 2.2 エッジ種別

| 種別 | 向き | 生成ルール |
| --- | --- | --- |
| `contains` | doc → func / flow / entity | スライドが定義・記載している要素 |
| `implements` | func → flow | 新機能一覧「新業務フロー該当箇所」列 |
| `uses` | flow → func | 業務フロー本文中の `[NN-NN]` 参照 |
| `authorizes` | doc(権限一覧) → func | 機能IDによる突合 |
| `dataflow` | system → entity → func | データフロー図・システム関連図の矢印 |
| `performs` | actor → flow(step) | 業務フローのステップ担当 |
| `next` | doc → doc | スライド連番（前後関係） |
| `parent` | folder → doc | フォルダ階層 |
| `refers` | doc → external / request | 外部資料・改善要望への言及 |
| `cooccur` | doc ↔ doc | 同一用語の共起（弱リンク、任意表示） |

## 4. アーキテクチャ / 技術選定

### 4.1 構成

```
replaceMd/
└─ viewer/
   ├─ build-index.mjs     … Node: md 走査 → 解析 → graph-data.js 出力
   ├─ graph-data.js       … 生成物（window.__REQ_GRAPH__ = {docs, nodes, edges, issues}）
   ├─ index.html          … ビューア本体
   ├─ app.js              … UI・グラフ描画
   ├─ parser.js           … md/表パーサ、ID正規化（build と共用）
   └─ style.css
```

### 4.2 技術選定と理由

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| **配信方式** | `<script src="graph-data.js">` で埋め込み | `file://` では `fetch()` が CORS でブロックされるが **script タグは読める**。→ **index.html をダブルクリックするだけで動く**（サーバ不要） |
| **フォールバック** | `<input type="file" webkitdirectory>` によるブラウザ内解析 | Node が使えない環境でもフォルダ選択で再インデックス可能 |
| **外部ライブラリ** | **ゼロ依存**（Vanilla JS + SVG/Canvas） | 社内オフライン環境で CDN 不可の可能性。力学レイアウトは自前実装（~150行）で十分。単一フォルダをコピーするだけで配布可能 |
| **グラフ描画** | ノード数 < 200 は SVG、それ以上は Canvas に自動切替 | SVG は DOM イベントが楽、Canvas は大量ノードで高速 |
| **Markdown 描画** | 自前の軽量レンダラ（見出し・表・リスト・`<br>` のみ対応） | 対象 md の記法が限定的なため、フルスペックの marked.js 等は不要 |
| **検索** | 転置インデックスをビルド時生成 | 182 ファイル程度なら線形走査でも足りるが、bigram インデックスで日本語部分一致を高速化 |

### 4.3 解析パイプライン（build-index.mjs）

```
1. 走査      : 01_要件定義書/**/*.md を再帰列挙
2. メタ抽出  : ファイル名 → スライド番号・タイトル、本文1行目 → デッキ名
3. 分類      : タイトルの章番号（2.2.3 等）で ドキュメント種別を判定
               → 新機能一覧 / 業務フロー一覧 / 業務フロー詳細 / 取扱データ / 権限一覧 / 図 / その他
4. 種別別パース:
   - 新機能一覧    → 表を行分割し 機能ID・機能名・区分・業務フロー参照列 を抽出
   - 権限一覧      → 機能ID（<br>分割）・ロール別権限マトリクスを抽出
   - 業務フロー詳細 → ステップ行から アクター・`[NN-NN]`参照・システム名 を抽出
   - 取扱データ    → エンティティ名・区分・主なデータ項目 を抽出
   - 図系          → 矢印記法（`->`, `$\rightarrow$`, `<->`）から システム間フローを抽出
5. 正規化    : §1.3 の全ルールを適用
6. 名前解決  : 参照文字列 → ノードID に解決。失敗分は issues[] に未解決として記録
7. 出力      : graph-data.js（ノード・エッジ・本文・検索インデックス・issues）
```

## 5. 実装計画

| Step | 内容 | 成果物 | 目安 |
| --- | --- | --- | --- |
| **S1** | `parser.js` — md 走査・表パース・ID正規化 | 正規化ルール §1.3 を実装。CLI で件数を出力し実データで検証 | 中 |
| **S2** | `build-index.mjs` — グラフ構築・名前解決 | `graph-data.js` 生成。未解決参照の件数レポートで精度確認 | 中 |
| **S3** | `index.html` + 3ペインレイアウト・ドキュメントビュー | F-02〜F-04（エクスプローラ / 本文 / 参照パネル） | 中 |
| **S4** | 検索・逆引き・ナビゲーション | F-05〜F-07。ここで **MVP 完成 = 実用開始可能** | 小 |
| **S5** | グラフビュー（力学レイアウト・フォーカス・フィルタ） | F-08〜F-10 | 大 |
| **S6** | マトリクス / データフロー / パス探索 | F-11〜F-13 | 中 |
| **S7** | 品質レポート・エクスポート | F-14〜F-19 | 中 |

**推奨**: S1〜S4（MVP）を先に完成させて実データで確認 → 抽出精度を調整してから S5 以降へ。
グラフを先に作ると、パース精度が低いまま見た目だけ整った「間違った関係図」ができるリスクが高い。

## 6. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| **md の一部が AI による画像再構成**（`※このスライドは LM Studio が PNG画像から再構成` の注記あり） | 抽出した関係が原本と異なる可能性 | 再構成注記のあるドキュメントに **信頼度バッジ**を表示。関係の根拠となった原文行を常に併記し、人間が検証できるようにする |
| 業務フロー名の不一致（取込/登録 等） | リンク切れ | フロー**番号**を主キーにする（§1.3）。名称一致は補助 |
| 丸数字参照（媒体Web化）の解釈 | 誤リンク | 丸数字→フローグループの対応表を `config.js` に外出しし、目視で調整可能にする |
| 表のセル結合による空 ID | 機能行の取りこぼし | 直前の非空 ID を引き継ぐ「forward-fill」処理を実装 |
| フォルダ重複（1.2 基本方針） | 重複ノード | 内容ハッシュで同一判定し統合 |
| 「オバートリップ」等の名称が今後また変わる | 辞書の陳腐化 | システム名・アクター名の辞書を `config.js` に外出し |
